The ROOTKey API accepts two kinds of credential. Use the one that matches who is calling:

| | API key | Personal access token |
| --- | --- | --- |
| **Header** | `x-api-key: YOUR_API_KEY` | `Authorization: Bearer rk_pat_YOUR_TOKEN` |
| **Acts as** | Your organization, through the user account that created the key | The person who created the token, in one organization at a time |
| **Made for** | Your servers and integrations | An AI agent or a script that works on a person's behalf, such as the [ROOTKey MCP server](/pages/integrations/claude-mcp) |
| **Created in** | Developer Tools | Account Settings |
| **Limited by** | The access of the user account | The user's own access, the token's scopes, and the policy of each organization |

Send one credential per request. A request that carries both an `x-api-key` and a personal access token is refused with [`conflicting_credentials`](/api-reference/errors#conflicting_credentials).

# API keys

The ROOTKey API uses API keys to authenticate requests.

You can view and manage your API keys in Developer Tools on ROOTKey Platform. See [API Keys](/pages/api-keys) for how to create one.

API requests are authenticated using a custom header. To authenticate a request, provide the key in the `x-api-key` header of the request:

```http
x-api-key: YOUR_API_KEY
```

API Keys are tied to the ROOTKey user account for which they were created. **An API key provides the same level of access & privileges that its associated ROOTKey user account would have.**

<Warning>
Please be sure to keep your API Keys secure! Do not share them in emails, chat messages, client-side code or publicly accessible sites.

If you have accidentally shared an API Key publicly, you can revoke it in the [Account Settings](https://app.rootkey.ai/settings/dev?utm_source=api_docs&utm_medium=authentication_page&utm_content=account_settings) of your ROOTKey user account by clicking the X button beside the key.
</Warning>

# Personal access tokens

A personal access token lets an AI agent or a script act as you, without sharing your password or an API key. It acts as the user who created it and it can never do more than that user can do in the ROOTKey app. Three more limits apply on top of your own access: the scopes you gave the token, the organizations you chose for it, and the agent policy that each organization sets.

A token works in one organization per request, and you name that organization in a header.

## Create a token

<Steps>
  <Step title="Open Account Settings">
    Sign in to [app.rootkey.ai](https://app.rootkey.ai/sign-in?utm_source=api_docs&utm_medium=authentication_page&utm_content=personal_access_tokens) and open your **Account Settings**. Under **Third-party access**, go to the **Personal access tokens** tab and click **Create token**.

    <img style={{ borderRadius: "2px" }} src="/images/tokens/01-tokens-tab.png" alt="Account Settings, Personal access tokens tab with Create token" />
  </Step>

  <Step title="Name it">
    Give the token a name that tells you which tool uses it, for example `Claude Desktop on my laptop`. Use one token per tool, so you can revoke one without touching the others. A name is at most 64 characters, and two of your active tokens cannot share one.

    <img style={{ borderRadius: "2px" }} src="/images/tokens/02-name-scopes.png" alt="Create personal access token with the name and the Read, Write and Delete scopes" />
  </Step>

  <Step title="Choose what it can do">
    Pick the [scopes](#scopes). **Read** is always included. **Write** and **Delete** are optional: grant them only to tools you trust.
  </Step>

  <Step title="Choose where it works">
    Choose the organizations the token may reach, or **All my organizations**, which also covers organizations you join later. A token reaches only the organizations you choose, and each organization can still restrict or block agents; see [What an organization controls](#what-an-organization-controls).

    <img style={{ borderRadius: "2px" }} src="/images/tokens/03-organizations-expiry.png" alt="Where it works and Expires after" />
  </Step>

  <Step title="Set when it expires">
    Choose how long the token lives, from 1 to 90 days. It stops working on its own after that, and it never lasts longer than 90 days. To keep a tool connected, create a new token before the old one expires.
  </Step>

  <Step title="Confirm it is you">
    ROOTKey asks you to confirm before it creates the token. If you have two-factor authentication, enter the 6-digit code from your authenticator app, or a backup code. Otherwise enter the 6-digit code that ROOTKey emails to you, which works once and expires after 10 minutes. Then click **Verify and create token**.

    <img style={{ borderRadius: "2px" }} src="/images/tokens/04-confirm.png" alt="Confirm it is you, with the 6-digit code" />
  </Step>

  <Step title="Copy the token">
    The token is shown once. Copy it now and store it like a password, in a password manager or a secret store. ROOTKey cannot show it again. If you lose it, revoke it and create a new one.
  </Step>
</Steps>

You can have up to 25 active tokens.

<Warning>
A token that can delete can remove data on your behalf, and anyone who holds a token acts as you. Never put it in client-side code, a repository, an email or a chat message.
</Warning>

## Use a token

Send the token in the `Authorization` header, and the organization it acts in in the `X-RootKey-Organization` header:

```http
Authorization: Bearer rk_pat_YOUR_TOKEN
X-RootKey-Organization: YOUR_ORGANIZATION_ID
```

For example, to list the vaults you can see in an organization:

```bash
curl https://api.rootkey.ai/api-v1/vaults \
  -H "Authorization: Bearer rk_pat_YOUR_TOKEN" \
  -H "X-RootKey-Organization: YOUR_ORGANIZATION_ID"
```

Three calls help a script or an agent find its way:

| Call | What it tells you |
| --- | --- |
| [`GET /me`](/api-reference/platform/endpoint/identity/get-me) | Who the token acts as, its scopes, the organizations it was limited to and when it expires. It needs no organization header. |
| [`GET /organizations`](/api-reference/platform/endpoint/identity/list-organizations) | The organizations the token can act in, with the ids to send in `X-RootKey-Organization`, each organization's agent mode and whether you are blocked. It needs no organization header. |
| [`GET /organization`](/api-reference/platform/endpoint/identity/get-organization) | The organization named by the header, and the scopes the token effectively has there right now. |

Only a personal access token can call these three: a request with an API key gets the `404` that any unknown path gets.

### The organization header

`X-RootKey-Organization` is required on every endpoint that works inside an organization. Without it the request gets [`organization_header_required`](/api-reference/errors#organization_header_required). The header is the only place the organization is read from: a query string or a body field does not count. An API key belongs to exactly one organization, so it ignores the header.

### Test and live data

A token works on live data unless a request sends `x-test-mode: true`, which makes it work on the organization's test data instead. Only this header decides, never a query string or a body field. See [Test and Live Data](/pages/environments).

## Scopes

A scope is a permission you give the token when you create it. You cannot change a token's scopes afterwards: create a new token instead.

| Scope | Lets the token | Endpoints |
| --- | --- | --- |
| `rootkey.read` | See what you can see | List and fetch vaults, tables, files, file versions, file history and validations, records and their versions, history and validations; download a file; validate a file; list deleted vaults, files and records; list recovery points; ask for access to Restricted data ([`POST /agent-step-ups`](/api-reference/platform/endpoint/agents/request-restricted-access) and [`GET /agent-step-ups/{stepUpId}`](/api-reference/platform/endpoint/agents/get-restricted-access)) |
| `rootkey.write` | Create and update | Create a vault, update a vault, create a file or a file version (including [direct uploads](/api-reference/platform/endpoint/files/direct-uploads)), create a record, queue a file audit report |
| `rootkey.delete` | Delete | Delete a vault or a file, and restore a deleted vault, file or record (a restore undoes a delete). A token cannot delete a record: see [below](#not-available-to-personal-access-tokens) |

A request that needs a scope the token does not carry gets [`insufficient_scope`](/api-reference/errors#insufficient_scope). `GET /me` and `GET /organizations` need no scope, and `GET /organization` needs `rootkey.read`.

A token also never has more access than its user. The user's role and teams in the organization decide what the request can reach, exactly as in the ROOTKey app, and a request that the role does not allow gets [`insufficient_permission`](/api-reference/errors#insufficient_permission).

## What an organization controls

An organization decides whether and how agents can use its data. Its administrators set an **agent access mode** in the organization's **AI agents** settings:

| Mode | What a token can do there |
| --- | --- |
| **Off** | Nothing. No personal access token is served, whoever created it. |
| **Read only** | Read what the member who created the token can read. Nothing can be created, changed or deleted. This is the mode until an administrator chooses another. |
| **Full access** | Read, create, change and delete, within the member's own permissions and the token's scopes. |

An organization can also:

- **Switch off personal access tokens.** No personal access token works in the organization from that moment, including tokens created later.
- **Require two-factor authentication.** Only members who have turned on two-factor authentication can use agents there.
- **Block a member's agents.** Every token that member created stops working in that organization at once. The member keeps their own access in the app, and an administrator can unblock them at any time.
- **Ask for approval of every delete.** With **Delete approval** on, an agent's delete of a file or a vault is refused with [`agent_approval_required`](/api-reference/errors#agent_approval_required) until the member the agent acts for approves it in the ROOTKey app, with a fresh two-factor check. Then the same request runs once. See [Delete approvals](/pages/integrations/delete-approvals).
- **Let members open Restricted data to their own agents.** Off by default. See below.

**Restricted** vaults and tables are listed with `agentAccessible: false`, so an agent can tell you they exist. With the option that lets members open Restricted data to their own agents off, which is the default, every request that would read or change them is refused with [`agent_restricted_data_denied`](/api-reference/errors#agent_restricted_data_denied). With it on, a read or a write is refused with [`agent_step_up_required`](/api-reference/errors#agent_step_up_required) until the member approves that one vault or table, for a few minutes, with a fresh two-factor check. Deleting and restoring Restricted data is never available to an agent, even with an approval. See [Restricted data and agents](/pages/integrations/restricted-step-up). The organization's [IP access rules](/api-reference/errors#access_policy_denied) apply to a token's requests like any other.

<Note>
Your organization governs the credentials it delegates to agents, not the AI itself: an agent using a person's own browser session, or a script holding an organization API key, cannot be told apart from that person.
</Note>

When an organization refuses a request, the error says why, and [`GET /organizations`](/api-reference/platform/endpoint/identity/list-organizations) shows each organization's mode and whether you are blocked, so a client can tell you what to ask an administrator for instead of retrying. The codes are on the [Errors](/api-reference/errors#personal-access-tokens-and-agents) page.

## Not available to personal access tokens

Some endpoints are never available to a personal access token, whatever the organization allows. A request that carries one is refused with [`agent_route_not_available`](/api-reference/errors#agent_route_not_available). Use an API key or the ROOTKey app for these:

- Deleting a record.
- Recovery points: fetch, download, create and delete. A token can only list them.

A token can list and restore what is in the trash ([`GET /files/deleted`](/api-reference/platform/endpoint/files/list-deleted-files), [`GET /records/deleted`](/api-reference/platform/endpoint/records/list-deleted-records), [`GET /vaults/deleted`](/api-reference/platform/endpoint/vaults/list-deleted-vaults) and the matching restore calls). Deleted tables, and anything of a Restricted vault or table, are restored by a person in the ROOTKey app. See [Trash and restore for agents](/pages/integrations/agent-trash-and-restore).

A token also cannot change a vault's data classification: that stays with a person in the app ([`agent_classification_change_not_allowed`](/api-reference/errors#agent_classification_change_not_allowed)).

## Revoke a token

Open **Account Settings** → **Personal access tokens**, click the actions menu of the token and choose **Revoke token**. Anything that uses it stops working on its next request, and a revoked token cannot be restored. The list shows each token's scopes, organizations, expiry, status and when it was last used. The last-used time updates every few minutes, so a token used a moment ago may still show **Never**.

A token that is missing, malformed, unknown, revoked or expired gets one identical `401`, so the response never says which of them it was.
