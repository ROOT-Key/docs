The ROOTKey MCP server connects Claude to your ROOTKey workspace. It implements the [Model Context Protocol](https://modelcontextprotocol.io), the open standard Claude uses to talk to external systems, and turns the documented ROOTKey REST API into tools Claude can call.

Ask Claude to anchor a contract, check whether a file still matches its proof, or pull the audit trail for a record, and it happens in your real workspace. The server signs in with your own [personal access token](/api-reference/auth#personal-access-tokens), so every tool call is an ordinary API request made as you. It can never do more than you can do in the ROOTKey app, everything it does is visible in the ROOTKey dashboard, and the organization it acts in decides whether agents may use its data at all.

<Tip>
  Prefer not to manage a token? The [hosted connector](/pages/integrations/hosted-connector) lets Claude, or any MCP client that supports remote servers, connect by signing in to ROOTKey, and you choose the organizations and permissions on a consent screen. This page covers the local server, which uses a personal access token.
</Tip>

<Note>
  The server runs locally on your machine and talks directly to `api.rootkey.ai`. Your token stays in your own environment: it is never sent to Anthropic, and it is sent to ROOTKey only as the credential of the API call itself.
</Note>

## Requirements

- **Node.js 20 or newer** on the machine running Claude
- **A ROOTKey personal access token.** Create one in the ROOTKey app under **Account Settings → Personal access tokens**. It starts with `rk_pat_`, it is shown once when you create it, and it lasts at most 90 days. You choose its [scopes](/api-reference/auth#scopes), the organizations it may reach and when it expires; [Authentication](/api-reference/auth#create-a-token) walks through each step.
- **An organization that lets agents in.** Each organization decides whether, and how far, agents may use its data. Until an administrator chooses otherwise, an organization lets agents read and nothing more. See [What the organization decides](#what-the-organization-decides).

<Warning>
  A token acts as you. Treat it like a password: keep it in a password manager or a secret store, create one token per tool, and revoke it under **Account Settings → Personal access tokens** if you suspect it leaked.
</Warning>

Since version 0.3.0 the server accepts only a personal access token. Organization API keys still work with the [REST API](/api-reference/auth), but not with this server: see [Upgrading from an API key](#upgrading-from-an-api-key).

## Install

Replace `your_personal_access_token` with the token you created. `ROOTKEY_ORGANIZATION` is optional; see [Choosing the organization](#choosing-the-organization).

<Tabs>
  <Tab title="Claude Code">
    Export the token in your shell profile or load it from your secret manager, then run this once, from anywhere:

    ```bash
    claude mcp add rootkey \
      --env ROOTKEY_TOKEN=$ROOTKEY_TOKEN \
      --env ROOTKEY_ORGANIZATION=your_organization_id \
      -- npx -y @rootkey/mcp
    ```

    Your shell expands the token, so it never appears in the command you type. Claude Code keeps the value in its own configuration on your machine.

    Start a new session and ask Claude what ROOTKey tools it has.
  </Tab>

  <Tab title="Claude Desktop">
    Claude Desktop keeps the token in plain text in its configuration file, so treat that file like a password. Open **Settings → Developer → Edit Config** and add the server to `claude_desktop_config.json`:

    ```json
    {
      "mcpServers": {
        "rootkey": {
          "command": "npx",
          "args": ["-y", "@rootkey/mcp"],
          "env": {
            "ROOTKEY_TOKEN": "your_personal_access_token",
            "ROOTKEY_ORGANIZATION": "your_organization_id"
          }
        }
      }
    }
    ```

    On **Windows**, route the command through `cmd` so `npx` resolves correctly:

    ```json
    {
      "mcpServers": {
        "rootkey": {
          "command": "cmd",
          "args": ["/c", "npx", "-y", "@rootkey/mcp"],
          "env": {
            "ROOTKEY_TOKEN": "your_personal_access_token",
            "ROOTKEY_ORGANIZATION": "your_organization_id"
          }
        }
      }
    }
    ```

    Restart Claude Desktop for the change to take effect.
  </Tab>

  <Tab title="Cursor and other clients">
    The server speaks MCP over stdio, so any client that can start a local program can use it. Run `npx -y @rootkey/mcp` with `ROOTKEY_TOKEN` in the process environment, in whatever shape that client's configuration takes. In Cursor, add this under `"mcpServers"` in `.cursor/mcp.json`:

    ```json
    "rootkey": {
      "command": "npx",
      "args": ["-y", "@rootkey/mcp"],
      "env": {
        "ROOTKEY_TOKEN": "your_personal_access_token",
        "ROOTKEY_ORGANIZATION": "your_organization_id"
      }
    }
    ```

    The [Agent Setup](/agent-setup/prompt) page has the equivalent entry for Codex, GitHub Copilot in VS Code, Windsurf and OpenCode.
  </Tab>

  <Tab title="Shared with a team">
    Commit a `.mcp.json` file at the root of your repository and let each person supply their own token from their environment:

    ```json
    {
      "mcpServers": {
        "rootkey": {
          "command": "npx",
          "args": ["-y", "@rootkey/mcp"],
          "env": { "ROOTKEY_TOKEN": "${ROOTKEY_TOKEN}" }
        }
      }
    }
    ```

    A personal access token belongs to one person, so never commit a token and never share one between people: everyone creates their own.
  </Tab>
</Tabs>

## Choosing the organization

A personal access token can reach several organizations, so the server never guesses which one you mean. There are three ways to choose:

- **Set a default.** Put the organization id in `ROOTKEY_ORGANIZATION`, and every tool uses it.
- **Name it in the request.** Every tool that works inside an organization takes an optional `organization` argument that overrides the default for that call.
- **Ask.** With neither, a tool answers that no organization is selected, and Claude calls `rootkey_list_organizations` and asks you which one to use. The list shows each organization's id, its agent mode (`DISABLED`, `READ_ONLY` or `FULL`) and whether you are blocked from agents there. Organizations that refuse agents are listed too, so you can see why.

A change Claude makes always reports the organization it acted in (for example `Acted in organization ...`), so a wrong default cannot go unnoticed.

<Tip>
  Create the token with the explicit list of organizations you need rather than **All my organizations**, and with only the scopes you need. The `organization` argument can name any organization the token covers, and a model that has read a malicious document could use that.
</Tip>

## Configuration

Every setting is an environment variable on the server process.

| Variable | Default | Description |
|---|---|---|
| `ROOTKEY_TOKEN` | required | Your personal access token (`rk_pat_` followed by 64 hexadecimal characters), sent as a Bearer token. The server exits immediately if it is missing or malformed, and never prints it. |
| `ROOTKEY_ORGANIZATION` | - | Default organization id for the token. A tool's own `organization` argument overrides it for that call. |
| `ROOTKEY_TEST_MODE` | unset (live) | `true` or `false`: whether the token works on your organization's test data or its live data. The two are separate, and live is the default. See [Test and Live Data](/pages/environments). |
| `ROOTKEY_ENV` | `production` | Optional. `production` is the only accepted value, and the server refuses to start with `development`. ROOTKey has one public API. |
| `ROOTKEY_API_URL` | - | Full base URL including the `/api-v1/` path. Use it for a self-hosted or on-premise deployment. Plain `http://` is accepted only for loopback hosts, since the credential travels in a header. |
| `ROOTKEY_READ_ONLY` | `false` | When `true`, only the 20 read tools are registered, and downloads may only write inside `ROOTKEY_DOWNLOAD_DIR`. |
| `ROOTKEY_TIMEOUT_MS` | `30000` | Timeout for ordinary requests, in milliseconds. |
| `ROOTKEY_TRANSFER_TIMEOUT_MS` | `300000` | Timeout for uploads and downloads, in milliseconds. |
| `ROOTKEY_DOWNLOAD_DIR` | `~/Downloads` | Where downloads are saved when no path is given. |
| `ROOTKEY_ALLOWED_DIRS` | home, temp, cwd | Directories uploads may read from, separated by `;` on Windows and `:` elsewhere. |
| `ROOTKEY_LOG_LEVEL` | `info` | `silent`, `error`, `warn`, `info` or `debug`. Logs are written to stderr. |

There is one public API, `https://api.rootkey.ai/api-v1/`, and no separate development environment. Whether you work on test or live data is a property of the credential, not of a host: a token follows `ROOTKEY_TEST_MODE`. To try things out, set `ROOTKEY_TEST_MODE=true`. A `ROOTKEY_ENV=development` left over from an earlier version of the server is rejected with a configuration error; remove the variable.

## What the organization decides

Your token is yours, but the organization decides whether an agent may use its data. An organization administrator sets this under **Organization Settings → AI agents**; the [admin guide](/pages/integrations/ai-agents) describes every setting. What it means for you:

| Setting | What your agent can do |
|---|---|
| **Off** (`DISABLED`) | Nothing in that organization. Every call is refused. |
| **Read only** (`READ_ONLY`) | Read what you can read. Creating, changing or deleting is refused. This is the setting until an administrator chooses another. |
| **Full access** (`FULL`) | Read, create, change and delete, within your own permissions and your token's scopes. |

An organization can also stop accepting personal access tokens, require two-factor authentication from members who use agents, and block a member's agents. It can ask you to approve every delete your agent asks for (see [Delete approvals](/pages/integrations/delete-approvals)), and it can let you open one Restricted vault or table to your agent for a few minutes (see [Restricted data and agents](/pages/integrations/restricted-step-up)). Your role, your teams and the organization's IP and country rules still apply on top of all of this.

**Some things are never available to an agent, whatever the organization allows:**

- Deleting a record. Agents can restore a record that a person deleted, and cannot delete one.
- Fetching, downloading, creating or deleting a recovery point. Claude can only list them. Use the ROOTKey app for the rest.
- Deleting or restoring **Restricted** vaults and tables, or anything in them. They appear in `rootkey_list_vaults` and `rootkey_list_tables` with `agentAccessible: false` so that Claude can tell you they exist. Unless the organization lets you open Restricted data to your agent, nothing more: with that option on, you can approve reading and writing one vault or table at a time.
- Restoring a table. Deleted tables are restored in the ROOTKey app.
- Changing the data classification of a vault.

<Note>
  Your organization governs the credentials it delegates to agents, not the AI itself: an agent using a person's own browser session, or a script holding an organization API key, cannot be told apart from that person.
</Note>

## Available tools

32 tools: the operations of the [API Reference](/api-reference/overview) that an agent may use, the listings that find what to operate on, and one diagnostic. Every tool except `rootkey_list_organizations` takes the optional `organization` argument. Deleting a record and every recovery point operation except the listing are not offered, because the API refuses them to agents.

- **The hosted connector gets 28.** The same as a token, without the four tools that read or write the local disk of the machine running the server: `rootkey_upload_file`, `rootkey_upload_file_version`, `rootkey_validate_file` and `rootkey_download_file`.

Every tool name is prefixed `rootkey_`, so it cannot be confused with a same-named tool from another MCP server in the same session. The **Scope** column is the scope your token needs for the call; a token that lacks it gets [`insufficient_scope`](/api-reference/errors#insufficient_scope).

### Organizations

| Tool | Scope | What it does |
|---|---|---|
| `rootkey_list_organizations` | none | List the organizations the token can act in, with each one's agent mode and whether you are blocked |

### Vaults

| Tool | Scope | What it does |
|---|---|---|
| `rootkey_list_vaults` | `rootkey.read` | List the vaults you can see, with address, name, classification and status |
| `rootkey_create_vault` | `rootkey.write` | Create a vault and return its address |
| `rootkey_update_vault` | `rootkey.write` | Rename a vault or change its description. The old values are overwritten |
| `rootkey_delete_vault` | `rootkey.delete` | Move a vault and its files to the trash, recoverable until retention purges them |
| `rootkey_list_deleted_vaults` | `rootkey.read` | List the deleted vaults you can see, newest deletion first |
| `rootkey_restore_vault` | `rootkey.delete` | Bring a deleted vault back, with the files deleted with it |

### Files

| Tool | Scope | What it does |
|---|---|---|
| `rootkey_list_files` | `rootkey.read` | List files in a vault, filtered by name, date range or anchoring status |
| `rootkey_upload_file` | `rootkey.write` | Upload a local file into a vault and anchor it |
| `rootkey_get_file` | `rootkey.read` | Fetch one file with its hashes, transaction details and usage metrics |
| `rootkey_download_file` | `rootkey.read` | Download a file to local disk |
| `rootkey_delete_file` | `rootkey.delete` | Move a file to the trash, recoverable until retention purges it |
| `rootkey_list_file_versions` | `rootkey.read` | List every version of a file |
| `rootkey_upload_file_version` | `rootkey.write` | Upload a new version of an existing file |
| `rootkey_validate_file` | `rootkey.read` | Check a local copy against the anchor and return ownership, integrity and validity |
| `rootkey_get_file_history` | `rootkey.read` | Read the activity log for a file |
| `rootkey_get_file_validations` | `rootkey.read` | List past validations, with current and previous hashes |
| `rootkey_list_deleted_files` | `rootkey.read` | List the deleted files you can see, newest deletion first |
| `rootkey_restore_file` | `rootkey.delete` | Bring a deleted file back, with its versions. Its vault must not be deleted |
| `rootkey_generate_file_audit_report` | `rootkey.write` | Queue a NIS2 or DORA compliance report. It is delivered in the ROOTKey app |

### Records

| Tool | Scope | What it does |
|---|---|---|
| `rootkey_list_tables` | `rootkey.read` | List the tables you can see, with address, name, classification and status |
| `rootkey_list_records` | `rootkey.read` | List records in a table with their metadata |
| `rootkey_create_record` | `rootkey.write` | Write a record, or a new version of one |
| `rootkey_list_record_versions` | `rootkey.read` | List every version of a record |
| `rootkey_get_record_history` | `rootkey.read` | Read the activity log for a record |
| `rootkey_get_record_validations` | `rootkey.read` | List past validations of a record |
| `rootkey_list_deleted_records` | `rootkey.read` | List the deleted records you can see, or those of one table |
| `rootkey_restore_record` | `rootkey.delete` | Bring a deleted record back. Its table must not be deleted |

### Recovery points

| Tool | Scope | What it does |
|---|---|---|
| `rootkey_list_recovery_points` | `rootkey.read` | List the recovery points whose vaults you can all read. Creating, fetching, downloading and deleting one is done in the ROOTKey app |

### Restricted data

These two are useful only where the organization lets members open Restricted data to their agents. See [Restricted data and agents](/pages/integrations/restricted-step-up).

| Tool | Scope | What it does |
|---|---|---|
| `rootkey_request_restricted_access` | `rootkey.read` | Ask for access to one Restricted vault or table. It returns the link to give to the user, who approves it in ROOTKey |
| `rootkey_get_restricted_access_status` | `rootkey.read` | Check once, after the user says they approved, whether the request is approved. Never in a loop |

### Diagnostics

| Tool | Scope | What it does |
|---|---|---|
| `rootkey_get_environment_info` | none | Report the server version and the API address. With a token it also asks the API who you are and what the token may do: the user, the token name, its scopes and expiry, and, for the selected organization, its agent mode and the scopes that are effective there. Never reveals the token |

Every tool declares whether it only reads, whether it is destructive and whether repeating it is safe, so your client can ask before it runs one that changes something. The delete tools and `rootkey_update_vault`, which overwrites the previous name or description, are marked destructive.

## Prompts

Besides the tools, the server offers whole workflows your client can list, so you do not have to remember the sequence.

| Prompt | What it does |
|---|---|
| `anchor_folder` | Anchors every file in a local folder into a vault, confirming first and reporting what landed |
| `compliance_evidence_pack` | Gathers the anchor, activity history, validations and version chain for one file, and writes it up |
| `verify_local_copies` | Validates local files against their anchors and leads with the failures |

In read-only mode only `compliance_evidence_pack` is offered, since the others write.

## What to expect when using it

A few behaviours are worth knowing before your first session, because they follow from how the ROOTKey API works.

**Addresses come from the list tools.** `rootkey_list_vaults` and `rootkey_list_tables` page through what you can see: a vault holds files and a table holds records. With a token you see the vaults and tables of the teams you belong to, and organization owners and administrators see all of them. When `rootkey_create_vault` makes a new one, keep the address it returns.

**Files move through your own machine.** Uploads read from the local disk of the computer running the server, and downloads are written there and reported back as a file path. File contents are never pasted into the conversation, so a large PDF costs you nothing in context.

**File anchoring is asynchronous.** A newly uploaded file starts as `PENDING` and becomes `REGISTERED` once the anchor is confirmed, or `FAILED` if something went wrong. The create call returns before that happens.

**Only files are anchored on chain.** Records are stored, hashed and audited, and come back `REGISTERED` immediately: there is no pending phase and no transaction hash for a record.

**Uploads can only read from a few directories.** A file to be uploaded must sit in your home directory, the temp directory or wherever the server was started, and hidden directories inside those are refused. This matters because the path can be chosen by the model, and the model reads documents other people wrote. Widen it with `ROOTKEY_ALLOWED_DIRS`.

**Records are versioned by primary key.** Creating a record whose key column matches an existing record adds a version to it rather than creating a duplicate. Asking Claude to "try that again" after a create will produce a second version, which is usually not what you want.

**Names and contents are other people's words.** Organization, vault and file names, record contents and error text were written by someone, often not you. The server tells the model to treat them as data and strips control characters from listed names, but the model is the last line of defence: do not paste untrusted documents into a session that holds a token that can write or delete.

## Safety

<Warning>
  **Deletions need your confirmation.** `rootkey_delete_vault` and `rootkey_delete_file` move the item to the trash: it leaves every listing at once and stays recoverable until the retention policy purges it. Every delete is recorded in the activity log, and a file that was anchored keeps its on-chain proof either way. Both are marked as destructive so Claude asks for confirmation, but the final responsibility for approving them is yours.

  You can bring a deleted vault, file or record back in the ROOTKey app, and Claude can do it too with `rootkey_restore_vault`, `rootkey_restore_file` and `rootkey_restore_record`, if your token has the `rootkey.delete` scope. A restore never needs your approval. If your organization asks you to approve every delete, the delete is refused the first time, you approve it in the ROOTKey app under **Pending approvals**, and Claude then repeats the same call once: see [Delete approvals](/pages/integrations/delete-approvals).
</Warning>

### Keep the token narrow

A token with only `rootkey.read` cannot create or delete anything, whatever Claude is asked to do, and a token limited to one organization cannot be pointed at another. If a session only needs to look, create a read-only token. A token cannot be edited after it is created: to change its scopes or organizations, create a new one and revoke the old.

### Read-only mode

Setting `ROOTKEY_READ_ONLY=true` registers only the tools that read data. The write tools are not advertised at all, so Claude cannot call them, and downloads may only write inside the configured download directory.

```json
{
  "mcpServers": {
    "rootkey": {
      "command": "npx",
      "args": ["-y", "@rootkey/mcp"],
      "env": {
        "ROOTKEY_TOKEN": "your_personal_access_token",
        "ROOTKEY_ORGANIZATION": "your_organization_id",
        "ROOTKEY_READ_ONLY": "true"
      }
    }
  }
}
```

This is useful for analysis and reporting sessions where nothing should change. Treat it as a convenience rail rather than a security control: what a call can do is decided by the token's scopes and the organization's agent mode, not by this switch, so anything else holding the token can still do whatever the token allows.

## Upgrading from an API key

Version 0.3.0 accepts only a personal access token. A configuration that still sets `ROOTKEY_API_KEY`, or that puts an organization API key in `ROOTKEY_TOKEN`, stops the server at start-up with a message that says what to do. To move to a personal access token:

1. Create a personal access token with the scopes you need, covering the organization or organizations the key belonged to.
2. In your client configuration, replace `ROOTKEY_API_KEY` with `ROOTKEY_TOKEN`, and set `ROOTKEY_ORGANIZATION` to the organization id (`rootkey_list_organizations` shows it). If the key was a test key, add `ROOTKEY_TEST_MODE=true`.
3. Expect the organization's agent mode to apply. Under the default **Read only** mode, the write tools are refused until an administrator chooses **Full access**.

What changes with the token:

- **Removed tools.** `rootkey_delete_record`, `rootkey_create_recovery_point`, `rootkey_get_recovery_point`, `rootkey_wait_for_recovery_point`, `rootkey_download_recovery_point`, `rootkey_delete_recovery_point` and the `backup_workspace` prompt are gone: the API refuses them to agents. Use the ROOTKey app for them. `rootkey_list_recovery_points` stays.
- **Your organization decides.** The organization's agent mode, its block list and its two-factor requirement apply to the token, and its scopes limit what a session can do.

The organization API key itself keeps working with the [REST API](/api-reference/auth). To stay on version 0.2 for now, run `npx -y @rootkey/mcp@0.2`.

## Troubleshooting

<AccordionGroup>
  <Accordion title="Claude does not show any ROOTKey tools">
    Confirm Node.js 20 or newer is installed and on the PATH (`node --version`), then restart the Claude client completely - configuration is read at startup. In Claude Desktop, check the MCP server logs under Settings → Developer; the server writes its startup line and any failure to stderr, which is what those logs show.
  </Accordion>

  <Accordion title="The server exits immediately">
    The server refuses to start, and says why on stderr, when `ROOTKEY_TOKEN` is missing or is not a whole personal access token (`rk_pat_` followed by 64 hexadecimal characters). It also refuses when `ROOTKEY_API_KEY` is set, or when `ROOTKEY_TOKEN` holds an organization API key: version 0.3.0 accepts only a personal access token (see [Upgrading from an API key](#upgrading-from-an-api-key)). Check that the variable is set inside the `env` block of the configuration, not only in your shell: Claude Desktop does not pass your shell environment to the server.
  </Accordion>

  <Accordion title="Every call returns 401">
    The API does not accept the token. It may have expired (a token lasts at most 90 days), been revoked, or belong to an account that was deactivated, and the API gives the same answer for all of these. Create a new token under **Account Settings → Personal access tokens** and update `ROOTKEY_TOKEN`. Ask Claude to run `rootkey_get_environment_info` to see the API address the server is using.
  </Accordion>

  <Accordion title="A tool says no organization is selected">
    The token can reach more than one organization and none was chosen. Ask Claude to call `rootkey_list_organizations` and tell it which one you mean, or set `ROOTKEY_ORGANIZATION` in the configuration. See [Choosing the organization](#choosing-the-organization).
  </Accordion>

  <Accordion title="A call is refused with an error that names a policy">
    Refusals from the organization, your role or the token are decisions, not faults. The tool error names the cause and what has to change, and Claude is told to relay it to you and stop: not to retry, and not to try the same thing in another organization. Each one has an entry in [Errors](/api-reference/errors#personal-access-tokens-and-agents):

    | Error code | What it means | What has to change |
    |---|---|---|
    | [`agent_access_disabled`](/api-reference/errors#agent_access_disabled) | The organization turned agent access off. | An organization administrator sets another mode. |
    | [`agent_write_not_allowed`](/api-reference/errors#agent_write_not_allowed) | The organization lets agents read only, and the call creates, changes or deletes. | An organization administrator allows **Full access**. |
    | [`agent_user_blocked`](/api-reference/errors#agent_user_blocked) | An administrator blocked your agents in this organization. Your own access in the app is unaffected. | An administrator unblocks you. |
    | [`agent_two_factor_required`](/api-reference/errors#agent_two_factor_required) | The organization requires two-factor authentication and you have not turned it on. | You turn it on under **Account Settings → Security**. |
    | [`agent_personal_tokens_disabled`](/api-reference/errors#agent_personal_tokens_disabled) | The organization does not accept personal access tokens. | An administrator allows them. |
    | [`agent_org_not_allowed`](/api-reference/errors#agent_org_not_allowed) | The token was not created for this organization. | Use an organization the token covers, or create a new token that includes this one. |
    | [`insufficient_scope`](/api-reference/errors#insufficient_scope) | The token lacks the scope the tool needs. | Create a new token with the scope. Scopes cannot be changed afterwards. |
    | [`insufficient_permission`](/api-reference/errors#insufficient_permission) | Your role does not grant what the call does. | An administrator changes your role. |
    | [`agent_restricted_data_denied`](/api-reference/errors#agent_restricted_data_denied) | The vault or table is classified Restricted and the organization does not let agents reach it, or the call deletes or restores it. | Use the ROOTKey app. Deleting and restoring Restricted data is never available to an agent. |
    | [`agent_step_up_required`](/api-reference/errors#agent_step_up_required) | The vault or table is classified Restricted, and the organization lets you open it to your agent. | You approve it in ROOTKey, using the link from `rootkey_request_restricted_access`. See [Restricted data and agents](/pages/integrations/restricted-step-up). |
    | [`agent_approval_required`](/api-reference/errors#agent_approval_required) | The organization asks you to approve every delete your agent asks for. Nothing was deleted. | You approve it in the ROOTKey app under **Pending approvals**, then Claude repeats the call once. See [Delete approvals](/pages/integrations/delete-approvals). |
    | [`agent_classification_change_not_allowed`](/api-reference/errors#agent_classification_change_not_allowed) | An agent cannot change a vault's data classification. | You change it in the ROOTKey app. |
    | [`agent_route_not_available`](/api-reference/errors#agent_route_not_available) | The operation is never available to agents, such as deleting a record or downloading a recovery point. | Use the ROOTKey app. |
    | [`access_policy_denied`](/api-reference/errors#access_policy_denied) | The organization id is wrong, you are not a member, or the organization's IP or country rules block this machine. The answer never says which. | Check the id with `rootkey_list_organizations`, or ask an administrator to review the access rules. |

    Not sure which one applies? Ask Claude to run `rootkey_get_environment_info`: it shows the organization's agent mode and the scopes your token has there.
  </Accordion>

  <Accordion title="An organization is missing from the list">
    `rootkey_list_organizations` lists the organizations you belong to that the token reaches, including those where agents are off or where you are blocked. An organization the token was not created for is not listed, and neither is one whose IP access rules block this machine. Create a token that includes the organization, or ask an administrator about the access rules.
  </Accordion>

  <Accordion title="A vault or table is listed but cannot be opened">
    It is classified Restricted. Restricted vaults and tables are listed with `agentAccessible: false` so that Claude can tell you they exist. Unless your organization lets you open Restricted data to your agent, no agent can read or change them, in any mode: open them in the ROOTKey app. If it does, Claude can ask you to approve one vault or table for a few minutes: see [Restricted data and agents](/pages/integrations/restricted-step-up). Deleting and restoring Restricted data stays in the ROOTKey app.
  </Accordion>

  <Accordion title="Most of the recovery point tools are missing">
    That is expected with a personal access token. An agent can only list recovery points, so the server offers `rootkey_list_recovery_points` and not the tools that fetch, download, create or delete one. `rootkey_delete_record` is missing for the same reason: the API refuses it to agents. Use the ROOTKey app for them.
  </Accordion>

  <Accordion title="Claude says a delete is waiting for my approval">
    Your organization asks you to approve every delete an agent asks for. Nothing was deleted. Open the ROOTKey app, go to **Pending approvals** and approve it with a fresh two-factor check, then tell Claude to repeat the call. Claude should do it once and not in a loop. See [Delete approvals](/pages/integrations/delete-approvals).
  </Accordion>

  <Accordion title="The server exits with a message about ROOTKEY_ENV">
    ROOTKey has one public API, so `ROOTKEY_ENV` accepts only `production` and is best left unset. A leftover `ROOTKEY_ENV=development` is refused at startup. Remove it, and set `ROOTKEY_TEST_MODE=true` to try things out on test data. For a self-hosted or on-premise deployment, set `ROOTKEY_API_URL` instead.
  </Accordion>

  <Accordion title="Requests fail with 429 Too Many Requests">
    A request went over a rate limit: your plan's API rate limit, or the limit of an operation that has its own - [Rate Limits](/pages/rate-limits) says which apply. The server automatically retries once the period indicated by the `Retry-After` header has passed, provided the wait is short. If 429s keep coming, spread those calls out over time, or move to a plan with a higher rate limit.
  </Accordion>

  <Accordion title="Requests fail with 503 Service Unavailable">
    ROOTKey was too busy to take the request for a moment. The server waits as long as the `Retry-After` header says and tries again, up to three attempts in all. It does this for listing and fetching, updating and deleting (GET, PUT and DELETE requests), but not for anything it sends as a POST, such as creating a file, a record or a vault: a repeat could create the same item twice. If one of those tools reports a 503, ask Claude to list the vault or table to see whether the item was created before you run the tool again. If a 503 keeps coming back, wait a little and try again, and contact [support@rootkey.ai](mailto:support@rootkey.ai) with the `requestId` the tool reports.
  </Accordion>

  <Accordion title="A tool reports the created file or record as null">
    The write succeeded. Several ROOTKey create endpoints do not return the id of what they created, so the server looks it up immediately afterwards; when anchoring has not yet surfaced the item, that lookup comes back empty. Ask Claude to list the vault or table again in a moment and the item will be there.
  </Accordion>

  <Accordion title="Windows: npx is not recognised">
    Use the `cmd /c` form of the Claude Desktop configuration shown in the Install section above. Windows needs the command routed through the shell for `npx` to resolve.
  </Accordion>
</AccordionGroup>

## Current limits

The server runs **locally**, which is what keeps your token on your machine. That has two consequences worth stating plainly.

- **It works in clients that can start a local program**, such as Claude Code, Claude Desktop and Cursor. For an app that connects to a remote server instead, such as Claude on claude.ai, use the [hosted connector](/pages/integrations/hosted-connector).
- **It covers the public API and nothing beyond it.** There are no tools for managing tokens, API keys or organization members. You manage tokens in the ROOTKey app, and organization settings are an administrator's job there.
