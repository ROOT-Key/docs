## Overview

**RKP-2 (Off-Chain)** is ROOTKey's high-performance data processing protocol. Data is processed and stored off-chain through ROOTKey's infrastructure, and each operation produces an off-chain integrity record - a SHA-256 hash of the payload with its timestamp and identifiers. Nothing is written to a blockchain.

The result is near real-time API response times with hash-based integrity verification. Verification compares a fresh hash of the data against the integrity record held by ROOTKey.

This protocol is designed for high-frequency write workloads, IoT and sensor data, operational telemetry, and any scenario where throughput and cost efficiency are primary constraints, but cryptographic integrity remains non-negotiable. When some records need independently verifiable on-chain evidence, use [RKP-3 (Hybrid)](/pages/protocols/rkp-3-hybrid) or [RKP-1 (Full On-Chain)](/pages/protocols/rkp-1-on-chain).

## Architecture Overview

```mermaid
flowchart TD
    A([Client Application]) -->|HTTPS / JSON| B[ROOTKey REST API]
    B --> C[Off-Chain Processing\n& Storage]
    C --> D[Off-Chain Integrity Record\nSHA-256 · Timestamp · Identifiers]
    C -->|Near real-time response| A
```

The API returns a response as soon as off-chain processing completes. There is no blockchain confirmation in the write path, so latency is not tied to block times or network fees.

Each integrity record includes:

- **SHA-256 hash** of the data payload
- **Timestamp** of the operation
- **Asset and operation identifiers**

Integrity verification is performed by re-hashing the stored data and comparing it against the integrity record.

## Validation Capabilities

| Validation Type | Supported |
|-----------------|-----------|
| Hash-based integrity verification | Yes |
| Proof of existence (off-chain integrity record) | Yes |
| On-chain proof of existence or integrity | No (no blockchain component) |
| Independent verification by third parties | Partial (requires the original data and access to the ROOTKey integrity record) |
| GDPR-compatible erasure of off-chain data | Yes |

Verification requires the original data asset and its integrity record. A party holding the data can confirm its integrity by recomputing the hash and comparing it to the record - but, unlike RKP-1 and RKP-3, the record is held by ROOTKey rather than on a public ledger.

---

## Strengths

- **High throughput** - designed for large-scale, high-frequency write workloads
- **Near real-time response** - no blockchain confirmation in the write path
- **Lowest cost per operation** - no gas fees, since nothing is written on-chain
- **GDPR erasure compatibility** - all data is off-chain and can be deleted
- **Scalable to IoT scale** - supports high-volume sensor and device data pipelines

---

## Weaknesses

- **No on-chain evidence** - there is no public-ledger record; verification relies on the ROOTKey integrity record rather than on a decentralised source of trust
- **Verification requires original data** - third-party verification needs both the data and access to the integrity record
- **Storage dependency** - verification depends on the availability of the off-chain integrity record
