## Overview

The ROOTKey REST API is the default integration model and the fastest path from zero to production. It exposes a JSON API over HTTPS with API key authentication and consistent error schemas, available across dedicated development and production endpoints.

No infrastructure setup is required on the client side. Authentication, protocol routing, and blockchain anchoring are handled by ROOTKey's cloud infrastructure.

This model is appropriate for any team building web-native, cloud-native, or service-oriented architectures - and for organisations that want to validate ROOTKey capabilities quickly before committing to a more embedded deployment.

## Architecture Overview

```mermaid
flowchart TD
    A([Client Application\nWeb · Mobile · Backend]) -->|HTTPS · JSON · API Key| B[api.rootkey.ai]
    B --> C[Authentication &\nPlan Limits]
    B --> D[Protocol Routing\nRKP-1 / RKP-2 / RKP-3]
    D --> E[(Blockchain Anchoring\n/ Off-Chain Processing)]
```

All API calls are authenticated using an `x-api-key` header. Development and production use separate base URLs and separate API keys. See [Environments](/pages/environments) for details.

## Integration Considerations

**Authentication and key management**
API keys should be stored as environment secrets and rotated regularly. Development and production keys are distinct and tied to their respective base URLs - never use a development key against the production endpoint, or vice versa.

**Rate limits and plan quotas**
Each plan has its own API rate limit, in requests per minute, and some operations, such as listing and restoring deleted items, have limits of their own. Over a rate limit the API answers `429 Too Many Requests` with a `Retry-After` header. Your plan also sets quotas, such as a monthly number of API requests: a request over a quota is refused with `usage_limit_exceeded`, and sending it again does not help until the quota resets or the plan changes. See [Rate Limits](/pages/rate-limits) for which limits apply.

**Error handling**
The API returns structured error responses with machine-readable codes. Branch on `errorCode` to decide whether to retry, and do not retry every `5xx` with backoff. A `429` or a `503` says in its `Retry-After` header how long to wait; wait that long, then retry. A `500` is different: an upload that failed with a `500` may still have been anchored, and `creation_outcome_unknown` must never be retried automatically. [Retrying a failed request](/api-reference/errors#retrying-a-failed-request) lists which failures are safe to retry and what to check first for an upload; the rest of the [Error Reference](/api-reference/errors) has the full error schema.

**Idempotency**
Operations that anchor data to the blockchain are not inherently idempotent - duplicate submissions result in separate on-chain records. Client-side deduplication should be implemented where appropriate.

**Webhook support**
Asynchronous operations (e.g. blockchain anchoring in RKP-1 and RKP-3) emit webhook events when complete. Configure webhook endpoints in the ROOTKey dashboard to receive real-time status notifications.
